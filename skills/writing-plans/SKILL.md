# 编写计划

## 概述

编写全面的实施计划，假设工程师对代码库零了解且品味存疑。记录他们需要知道的一切：每个任务要修改哪些文件、代码、测试、可能需要查看的文档、如何测试。以小粒度任务的形式给出完整计划。DRY、YAGNI、TDD、频繁提交。

假设他们是有经验的开发者，但对我们的工具集或问题域几乎一无所知。假设他们不太熟悉好的测试设计。

**开始时宣布：** "我正在使用编写计划技能来创建实施计划。"

**保存计划到：** `docs/plans/YYYY-MM-DD-<功能名>.md`
- （用户对计划位置的偏好优先于此默认值）

## 范围检查

如果规格覆盖了多个独立子系统，应该在头脑风暴阶段将其拆分为子项目规格。如果没有拆分，建议为每个子系统编写单独的计划。每个计划应该独立产出可工作、可测试的软件。

## 文件结构

在定义任务之前，先规划哪些文件将被创建或修改，以及每个文件的职责。这是锁定分解决策的地方。

- 设计具有明确边界和定义良好接口的单元。每个文件应有一个明确职责。
- 偏好更小、更聚焦的文件，而非做太多事情的大文件。
- 在现有代码库中，遵循已有模式。

## 小粒度任务

**每一步是一个动作（2-5 分钟）：**
- "编写失败的测试" — 一步
- "运行它确认失败" — 一步
- "编写最小代码使测试通过" — 一步
- "运行测试确认通过" — 一步
- "提交" — 一步

## 计划文档头部

**每个计划必须以此头部开始：**

```markdown
# [功能名] 实施计划

> **给代理工作者：** 必须使用 ccpowers:subagent-driven-development（推荐）或 ccpowers:executing-plans 来逐任务实施此计划。步骤使用复选框（`- [ ]`）语法跟踪。

**目标：** [一句话描述构建内容]

**架构：** [2-3 句关于方法]

**技术栈：** [关键技术/库]

---
```

## 任务结构

````markdown
### 任务 N：[组件名]

**文件：**
- 创建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

- [ ] **步骤 1：编写失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试验证失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL，提示 "function not defined"

- [ ] **步骤 3：编写最小实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试验证通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **步骤 5：提交**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: 添加具体功能"
```
````

## 禁止占位符

每一步都必须包含工程师需要的实际内容。以下是**计划失败** — 绝不要写它们：
- "待定"、"TODO"、"稍后实现"、"填充细节"
- "添加适当的错误处理" / "添加验证" / "处理边界情况"
- "为以上内容编写测试"（没有实际测试代码）
- "类似于任务 N"（重复代码 — 工程师可能不按顺序读）
- 描述做什么但不展示怎么做的步骤（代码步骤需要代码块）

## 记住
- 始终使用精确的文件路径
- 每步都有完整的代码 — 如果某步修改代码，展示代码
- 精确的命令和预期输出
- DRY、YAGNI、TDD、频繁提交

## 自审

写完完整计划后，以新鲜的眼光对照规格检查计划：

**1. 规格覆盖：** 浏览规格中的每个章节/需求。能指向实现它的任务吗？列出任何空缺。

**2. 占位符扫描：** 搜索计划中的危险信号 — "禁止占位符"部分中的任何模式。修复它们。

**3. 类型一致性：** 后续任务中的类型、方法签名和属性名是否与前面任务中的定义一致？

发现问题就内联修复。不需要重新审查 — 修复后继续。

## 执行交接

保存计划后，提供执行选择：

**"计划已完成并保存到 `docs/plans/<文件名>.md`。两种执行选项：**

**1. 子代理驱动（推荐）** - 每个任务分派一个新的子代理，任务间审查，快速迭代

**2. 内联执行** - 在当前会话中使用执行计划技能，批量执行带检查点

**选择哪种方式？"**

**如果选择子代理驱动：**
- **必须使用：** ccpowers:subagent-driven-development
- 每任务新子代理 + 两阶段审查

**如果选择内联执行：**
- **必须使用：** ccpowers:executing-plans
- 批量执行带审查检查点
