# 接收代码审查

## 概述

代码审查需要技术评估，而非情感表演。

**核心原则：** 实施前验证。假设前提问。技术正确性优先于社交舒适。

## 回应模式

```
收到代码审查反馈时：

1. 阅读：不做反应地完整阅读反馈
2. 理解：用自己的话复述需求（或提问）
3. 验证：对照代码库现实检查
4. 评估：对这个代码库技术上合理吗？
5. 回应：技术性确认或有理由的反驳
6. 实施：逐项实施，每项都测试
```

## 禁止的回应

**绝不要：**
- "你说得完全对！"（表演性的）
- "好观点！" / "优秀的反馈！"（表演性的）
- "让我现在就实施"（验证之前）

**应该：**
- 复述技术需求
- 提出澄清问题
- 如果有误，用技术理由反驳
- 直接开始做（行动 > 语言）

## 处理不清楚的反馈

```
如果任何项目不清楚：
  停下 — 不要实施任何东西
  对不清楚的项目提问

为什么：项目可能相关。部分理解 = 错误实施。
```

## 来源处理

### 来自用户
- **信任** — 理解后实施
- **仍然提问** 如果范围不清
- **不做表演性同意**

### 来自外部审查者
```
实施前：
  1. 对这个代码库技术上正确吗？
  2. 会破坏现有功能吗？
  3. 当前实施的原因是什么？
  4. 所有平台/版本都适用吗？
  5. 审查者理解完整上下文吗？

如果建议看起来有误：
  用技术理由反驳
```

## 实施顺序

```
多项反馈：
  1. 先澄清不清楚的全部内容
  2. 然后按此顺序实施：
     - 阻塞问题（崩溃、安全）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 逐项测试
  4. 验证无回归
```

## 何时反驳

当以下情况时反驳：
- 建议破坏现有功能
- 审查者缺少完整上下文
- 违反 YAGNI（未使用的功能）
- 对此技术栈技术上不正确
- 存在遗留/兼容性原因
- 与用户的架构决策冲突

## 底线

**外部反馈 = 待评估的建议，不是要遵循的命令。**

验证。质疑。然后实施。

不做表演性同意。始终保持技术严谨。
