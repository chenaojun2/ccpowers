# 系统化调试

## 概述

随机修复浪费时间并制造新 bug。快速补丁掩盖了底层问题。

**核心原则：** 在尝试修复之前，始终找到根本原因。症状修复是失败。

**违反这个流程的字面意思就是违反调试的精神。**

## 铁律

```
未经根因调查不得修复
```

如果你还没完成阶段 1，你不能提出修复方案。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况使用：**
- 时间压力下（紧急情况让猜测变得诱人）
- "就一个快速修复"看起来很明显
- 你已经尝试了多次修复
- 之前的修复不起作用

## 四个阶段

你**必须**在进入下一阶段前完成当前阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 能可靠触发吗？
   - 具体步骤是什么？
   - 每次都会发生吗？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查最近变更**
   - 什么变更可能导致了这个问题？
   - Git diff、最近的提交
   - 新的依赖、配置变更

4. **在多组件系统中收集证据**

   **当系统有多个组件时：**

   **在提出修复前，添加诊断检测：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每层的状态

   运行一次以收集证据，展示在哪里断裂
   然后分析证据以确定故障组件
   然后调查该特定组件
   ```

5. **追踪数据流**
   - 坏值来源于哪里？
   - 什么调用传入了坏值？
   - 持续向上追踪直到找到源头
   - 在源头修复，而非在症状处

### 阶段 2：模式分析

1. **找到工作示例** — 在同一代码库中找到类似的工作代码
2. **对照参考** — 完整阅读参考实现，不要略读
3. **识别差异** — 工作和损坏之间有什么不同？
4. **理解依赖** — 需要什么其他组件、设置、配置？

### 阶段 3：假设与测试

1. **形成单一假设** — 明确陈述："我认为 X 是根因，因为 Y"
2. **最小化测试** — 做最小可能的变更来测试假设
3. **继续前验证** — 有效？→ 阶段 4。无效？→ 新假设。不要在上面叠加更多修复。

### 阶段 4：实施

1. **创建失败的测试用例** — 必须在修复前有
2. **实施单一修复** — 处理已识别的根因。一次一个变更。
3. **验证修复** — 测试通过了？其他测试没坏？
4. **如果修复不起作用** — 停下。已尝试多少次修复？
   - 如果 < 3 次：返回阶段 1 重新分析
   - **如果 ≥ 3 次：停下并质疑架构**
5. **如果 3+ 次修复失败：质疑架构**
   - 这个模式是否根本不对？
   - 应该重构架构还是继续修复症状？
   - **在尝试更多修复前与用户讨论**

## 危险信号 — 停下并遵循流程

如果你发现自己在想：
- "先快速修复，之后再调查"
- "试着改一下 X 看看行不行"
- "同时添加多个变更，运行测试"
- "跳过测试，我会手动验证"
- "大概是 X，让我修复它"
- "我不完全理解但这可能有效"
- "再试一次修复"（已经尝试了 2+ 次）

**以上所有都意味着：停下。返回阶段 1。**

## 常见的自我合理化

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。流程对简单 bug 也很快。 |
| "紧急情况，没时间走流程" | 系统化调试比胡乱猜测更快。 |
| "先试这个，然后再调查" | 第一个修复定下了模式。从一开始就做对。 |
| "确认修复有效后再写测试" | 未测试的修复不持久。先测试证明它有效。 |
| "同时多个修复节省时间" | 无法隔离什么起了作用。导致新 bug。 |
| "再尝试一次修复"（2+ 次失败后） | 3+ 次失败 = 架构问题。质疑模式，不要再修。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|----------|----------|
| **1. 根因** | 读错误、复现、检查变更、收集证据 | 理解什么和为什么 |
| **2. 模式** | 找工作示例、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小测试 | 确认或新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 解决，测试通过 |
